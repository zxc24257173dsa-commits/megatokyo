# Phase 10：補貨建議

## 目的

告訴業主「哪些商品要補、補多少、最晚哪一天要下單」，並且每一個數字都能看到怎麼算出來的。

**只提供建議，系統不會自動下單。**「標記為已決定採購」只是一筆紀錄，不會對任何人下訂單，也不會建立採購批次。實際買了之後，照原本流程匯入成本試算表。

## 計算方式（日本買了直接寄美國）

資料只用到**最後一個完整的營業日**（美東時間），當天還沒結束的銷量不影響速度。

| 項目 | 算法 |
|---|---|
| 每日需求 v | 最近 7 天、14 天、30 天的平均「庫存需求」，以 50% / 30% / 20% 加權（Phase 8：組合商品拆成組成 SKU、贈品也算） |
| 需求波動 σ | 最近 30 天每日需求的標準差 |
| 交期 L | 在日本下單到美國可以賣：業主說 9–11 天，用保守的 **11 天**（可依 SKU 另設） |
| 涵蓋天數 R | 沒有固定下單日，每次採購多涵蓋 **7 天**（可設定） |
| 安全庫存 SS | z × σ × √L，z = 1.65（約 95% 不缺貨）；可依 SKU 手動指定 |
| 目標庫存 S | v × (L + R) + SS |
| 現有與快到的庫存 | 美國可售（已扣掉已付款訂單預留的）＋ 運送中 ＋ 已買但還沒從日本寄出 |
| 建議採購 | 目標 − 現有，依整箱數（case pack）與最小數量進位 |
| 最晚下單日 | 現有與快到的庫存扣掉安全庫存後還能撐的天數，再往前推一個交期 |

**運送中的貨只算「快到的庫存」，永遠不算美國可售。**

### 拆盒賣的卡片

在 SKU 頁設定了「盒內內容」的卡片（例如 PERONA promo）不是直接買來的：

- **卡片本身**不建議採購，而是建議「拆 N 盒」。N 不會超過美國實際有的盒數；不夠的部分會提醒要等盒子到貨。
- **盒子的需求** = 直接賣出的盒子 ＋ 為了盒內卡片要拆的盒子。
  - 每天要拆幾盒，取盒內「最快賣完」的那張卡決定：該卡每日需求 ÷ 每盒張數。
  - 過去的拆盒紀錄不再重複算成盒子需求。

### 新商品

- 銷售紀錄少於 14 天的商品，畫面會提醒需求可能不準。
- 可以在 SKU 補貨設定填「每日銷量」，用來估算還沒有銷售紀錄的新品。

## 狀態

| 狀態 | 意思 |
|---|---|
| 立刻處理（紅） | 已經到了或過了最晚下單日，或美國已經沒貨但還在賣 |
| 3 天內（橘） | 3 天內要下單 |
| 本週內（黃） | 在涵蓋天數內要下單 |
| 充足（綠） | 還早，或沒有需求 |

## 畫面（側邊欄 › 補貨建議）

- 「產生最新建議」會存成一份快照（`replenishment_runs`），之後設定或銷量改變，舊的建議也不會變。
- 每一列有「為什麼」，展開就是上面的算式和實際數字。
- 可以改建議數量，**必須填原因**；可以勾選後「標記為已決定採購」；兩者都有稽核紀錄，已決定的不能再改。
- 「匯出採購清單」：CSV，列出要買的 SKU、數量、原本的建議、修改原因、最晚下單日，可以直接給日本採購的人。
- 修改設定：交期、涵蓋天數、服務水準（90% / 95% / 98% / 99%）。

## 權限

| 動作 | 需要的權限 | 誰有 |
|---|---|---|
| 查看 | `replenishment.view` | 所有角色 |
| 產生建議、修改數量、標記已決定、修改設定 | `replenishment.edit` | 管理員、日本庫存管理員 |

## API

| 端點 | 內容 |
|---|---|
| `POST /api/v1/replenishment/runs` | 產生建議並保存 |
| `GET /api/v1/replenishment/runs/latest`、`/runs/{id}`、`/runs` | 讀取建議 |
| `PATCH /api/v1/replenishment/suggestions/{id}` | 修改數量（`{qty, reason}`） |
| `POST /api/v1/replenishment/runs/{id}/confirm` | 標記為已決定採購 |
| `GET /api/v1/replenishment/runs/{id}/purchase-list.csv` | 匯出採購清單 |
| `GET/PUT /api/v1/replenishment/settings` | 讀取／修改設定 |
| `PUT /api/v1/replenishment/skus/{id}` | SKU 補貨設定：不補貨、整箱數、最小數量、交期、手動每日銷量、安全庫存 |
